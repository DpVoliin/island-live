# 通知存活 & 后台存活

目标：**岛要一直在**（不会被划掉、不会被系统悄悄清掉），**进程也要一直在**（不会被当成后台应用回收）。

## 三个机制

| 机制 | 解决什么 | 实现 |
|---|---|---|
| ① **前台服务** | 系统回收后台进程时**不优先杀我们** | `LiveUpdateService`（`START_STICKY`）。关键是它认领的**就是岛本身那条通知** —— 同一个通知键，所以**不会多出一条多余的常驻通知** |
| ② **状态全量落盘** | 进程被杀后，能重建出**一模一样**的岛 | `LiveUpdateStore`：把渲染所需字段全部序列化（进程里只有 id + 截止时间是重建不出来的） |
| ③ **看门狗闹钟** | 通知被划掉 / 被系统清了 / 服务没被系统拉回来 | `LiveUpdateAlarmReceiver` 每 15 分钟查一次：`getActiveNotifications()` 里没有就**补回来**。走 `AlarmManager`，**进程死了照响** |

## 为什么前台服务的通知不会多出一条

`startForeground(id, notification)` 用的键是 `(null, id)`，而普通 `notify(tag, id, …)` 的键是 `(tag, id)` —— **是两个通知**。
所以库做了"**主通知**"设计：最新那条**不带 tag** 发，前台服务才能认领**同一条**。
（多路并存时，非主通知才带 tag；主通知被收回时会把剩下最新的那条提升为新的主通知。）

**顺带一说**：Android 16 起，平台本意就是"实时通知由前台服务承载" —— 所以这既是保活，也是**贴合平台规范**。

## 能活 / 活不了（诚实版）

| 场景 | 结果 |
|---|---|
| 系统内存紧张回收后台进程 | ✅ 活（前台服务优先级 + 被杀后系统拉回 + 看门狗兜底） |
| 用户把通知划掉 | ✅ 15 分钟内自动补回来 |
| 系统清理通知 | ✅ 同上 |
| 厂商省电策略杀后台 | 🟡 多数情况能活；仍建议**关闭电池优化 + 加自启动白名单** |
| 用户点「强行停止」 | ❌ 死。Android 的设计，任何应用都做不到自启，只有系统白名单能豁免 |
| 重启手机 | ❌ 不自动恢复（不主动冒出来，避免"重启后岛上突然多一条"）；下次进 App 会清掉过期残留 |

## 用户侧该做的（App 侧栏有按钮直达）

1. 侧栏 →「后台与通知存活」→ **电池优化** → 把本应用设为"不优化"
2. **应用信息** → 找到厂商的「自启动 / 后台运行」开关（小米叫"自启动"，华为叫"应用启动管理"）→ 允许
3. 最近任务里**给本应用加锁**（决定它不被一键清理）
4. 侧栏的**「立即检查」**可随时验证：会告诉你"进行中 N 条 · 通知还在 M 条 · 前台服务保活 开/关"

## 合规

前台服务类型用 `specialUse`（诚实归类：既不是数据同步也不是媒体播放，而是"维持一条进行中的实时状态通知"）。
上架时需在商店表单里说明用途；不想承担这个说明成本的，可用 `oss` 变体并关掉"前台服务保活"开关（那就只靠看门狗兜底，存活能力弱一些）。
